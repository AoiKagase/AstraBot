# P12 Release 実機クラッシュ 2026-09-12

受入状態: **元DLLはFAIL。修正版で今回の再現条件を通過、6症状の受入は継続中**。
P12の実機先行制約を維持する。

## 観測

- 対象DLL SHA256: `ba702d6b2202e8703e18dda58c52302e888ef4c4f88fb4e6829b72c43a7e3e7e`
- 最初の実機ダンプ: `hlds_3.13.0.788-dev-f955b07_crash_20260912_185955_1.mdmp` は0バイト。
- 同じDLLをx86 CDBで起動し、2BOT参加後のラウンド切替で `c00000fd`（stack overflow）を再現。
- 19:10:12 JSTの初回例外で完全ダンプを採取（207,170,979 bytes）。ローカル `.agent-state/p12-native-crash.dmp` に保管し、stageしない。
- 停止点はDLL RVA `0xA3327`、`__alloca_probe`。呼出し側return RVA `0x15D1D` は `invalidateCurrent` から `stopMotion` を呼んだ直後。
- TEB StackBase `0x00e00000`、StackLimit `0x00d01000`。SP `0x00d03288` で残量が足りず、ページprobeが失敗。
- 同じobjectからMAPのみ付けて再linkし、アドレスを対応付けた。テストプログラムは使用していない。

## 原因と修正

Releaseの生成コードで `LifecycleCoordinator::startFrame` が477,764 bytes、
`NavConsole::selectActor` が519,324 bytesをスタック確保する。
`selectActor` の `ActorState{}` 一時オブジェクトは、世代変更判定より前の関数入口で確保される。
これらが重なり、ラウンド再生成に伴う状態無効化・移動停止処理で約1MBのエンジンスタックを使い切る。

- `ActorState{}` の代入を、その場での破棄・placement newによる再構築に変更。
  ActorScopeが保持するアドレスを維持する。全体resetの同じ代入も修正する。
- フレーム入力配列をLifecycleCoordinatorの保持領域へ移し、各フレームで要素を初期化する。
- エンジンのスタック容量は変更しない。

## 検証

修正版SHA256: `4b40a04a6dfafa097f4b070f424414b3e7244d322d359c14938d6cc0668d41aa`。
Release x86ビルド成功、指定6エクスポート一致、配備後hash一致を確認。

生成コードの固定スタック確保量（プロローグ分などを除く）:

| 関数 | 修正前 bytes | 修正後 bytes |
|---|---:|---:|
| LifecycleCoordinator::startFrame | 477764 | 20940 |
| NavConsole::selectActor | 519324 | 16 |
| NavConsole::reset | 519384 | 2132 |

修正版をx86 CDB監視下のde_dust2で起動し、`astrabot_addbot 1`で2BOTにした。
修正前に落ちたラウンド2への切替を通過。その後、実機コンソールに `sv_restart 1` を
10回送り、各回で両BOTの処理継続とプロセス生存を確認した（ラウンド12まで）。
この間、アクセス違反・スタックオーバーフローは検出されなかった。
`crashfix-console.log` と `crashfix-runtime.json` に結果を記録。

この再現確認が成功しても6症状×120試行の受入やユーザーの明示的PASSを代替しない。
テストターゲット、CTest、canonical、commitは実施しない。
