Native CCSBot::TakeDamage (cs_bot.cpp98–168) reads pevInflictor as its source. It rebukes a human teammate before delegating to CBasePlayer::TakeDamage. Enemy injury updates attacker/time and safe time, guards shotgun repeats using attacker+timestamp and surprise, then performs FOV/visibility and optional panic RNG. It explicitly avoids direct Attack. An accepted HUD damage observation is not equivalent to this pre-base call.

A concrete HUD/entvars loss example: two same-frame human teammate calls with amounts3+2 and one call with amount5 can leave the same summed damage and final inflictor/health. Native FriendlyFire constructs/draws its delay once per call before duplicate admission, so two delay draws and one draw are different required behavior. This disproves the HUD/entvars-only reconstruction, not every conceivable combination of all public hooks. No lossless combined public bridge has been established in this audit. Injury remains open; substituting nearest-player guesses or aggregate post-damage reactions would not satisfy its native conditions.

The optional ReGameDLL provider subscribes to the public API 5.30 `CBotManager_OnEvent` hook for `EVENT_WEAPON_FIRED`, `EVENT_WEAPON_FIRED_ON_EMPTY`, and `EVENT_WEAPON_RELOADED`. The game dispatches these events after the native animation gates where applicable (`player.cpp` and the weapon implementations). The provider compares opaque player identities through the public engine interface. `UpdateClientData` and `GetWeaponData` supply the active weapon and M4A1/USP silencer state. The ranges and priorities are taken from `IsGameEventAudible` in `game_shared/bot/bot_util.cpp`. The knife-run reaction uses the event even for an acoustically silent weapon.

Standard GameDLL and servers without the dispatcher keep mapped `PlaybackEvent` and sound intake. `SendWeaponAnim` updates `weaponanim` separately and client prediction can suppress its `SVC_WEAPONANIM` message. These public observations do not establish the standard GameDLL's exact animation stream. The ReGameDLL intake uses confirmed prediction data per player. If that data stops being available, a fallback sample that already arrived can have been suppressed before the native firing callback detects the loss.

## Hostage rescue calls

The pinned reference's default target defines `REGAMEDLL_FIXES`. `HostageChatter` dispatches `EVENT_HOSTAGE_CALLED_FOR_HELP` with the hostage as the source. The dispatcher forwards that entity unchanged. The default arm in `CCSBot::OnEvent` rejects nonplayers before the later CT collection branch, and `CHostage` inherits the false `IsPlayer()` result. The collection branch is reachable only outside these default build semantics. ## Hostage use and current follow state

The pinned `CHostage::Use` emits `EVENT_HOSTAGE_USED` on an accepted start, including when `CHostageImprov::Chatter` suppresses speech because another hostage is speaking or its timer is still running. `Touched_A_Hostage` covers the initial accepted touch. The existing `PlayerPostThink` scope and qualified follow samples cover audible starts (12A).

`HostagePos` sends a refresh marker, a hostage index and position. `HostageK` removes a radar marker, and `ScenarioIcon` gives an optional living count. These messages carry no current follow state or leader. `CHostage::IsFollowing` reads private classic state or the improved state and its leader. The follow state's `RANDOM_FLOAT(125, 175)` call carries no player, hostage or event type.

The optional public ReGameDLL 5.30 bot-event hook consumes `EVENT_HOSTAGE_USED` after the native follow state changes and before the first-contact log. The argument identifies the CT. A validated start voice in the same PlayerUse scope can also supply the hostage generation. The event then uses the existing T report and guard decision. Vanilla uses the public sound and log fallback. This event provides no stop-follow notification or current follower query. Authoritative per-hostage follow status and escort counts remain open.

Unit 20 reuses the 12A receipt. A qualified voice supplies the accompanying hostage identity for that receipt only. After the report, the T considers all other living hostages in its tracked roster, including entities whose previous position is no longer remembered. Visibility is tested at the native point without a view-cone gate. Any visible hostage with unknown follow state defers the guard change. The first-touch log supplies the CT's location and can trigger the change when the T sees no living hostage.
